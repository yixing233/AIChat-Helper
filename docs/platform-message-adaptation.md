# 扩展各平台消息适配情况

本文档用于记录 **当前扩展版本** 对各个平台消息内容的适配情况，重点覆盖：

- 普通文本
- 公式
- 代码块
- 图片
- 思考过程

这里的“适配”主要指以下几类能力：

1. 能否从页面或网络 API 中正确提取消息
2. 能否在导出预览 / 备份库预览中较完整显示
3. 能否在导出文件中保留主要内容

## 状态说明

- `支持`：当前扩展已有明确适配，且已有对应实现或测试覆盖
- `部分支持`：能处理一部分场景，但仍依赖平台具体返回结构，或只在部分链路中表现完整
- `未适配`：当前没有明确适配逻辑，或尚未确认稳定可用

## 平台说明

### ChatGPT

| 类型 | 适配情况 | 说明 |
| --- | --- | --- |
| 普通文本 | 支持 | 当前主链路基于 `conversation` API 的 `mapping` 提取消息，并过滤内部工具提示、隐藏上下文和未完成草稿。 |
| 公式 | 支持 | 已对 `content_references` / `serialization_metadata` 中的 `latex` 做替换，导出 HTML 中也会渲染为公式块或行内公式。 |
| 代码块 | 支持 | `code` / `program` 等内容片段会转成 fenced code block，保留语言标记。 |
| 图片 | 支持 | 支持生成图、上传图、图片附件、图片占位文本、DOM 回填图片 URL、节点 hover 图片卡片、导出图片归档、备份图片缓存。 |
| 思考过程 | 部分支持 | 会过滤掉不少内部 reasoning / tool prompt / policy 文本，保留最终可见消息；但并没有像 DeepSeek 那样单独建模“思考过程消息”。 |

补充：

- 页面内节点轨道已支持图片型用户消息的 hover 预览。
- 对于纯图片型消息，当前也会进入轨道，不再因文本为空被丢弃。

### Claude

| 类型 | 适配情况 | 说明 |
| --- | --- | --- |
| 普通文本 | 支持 | 基于 Claude 会话 API 提取，包含普通问答文本。 |
| 公式 | 部分支持 | 若公式以普通 Markdown / 文本形式出现，可随消息导出与预览；但没有像 ChatGPT 那样做专门的 LaTeX 引用替换链路。 |
| 代码块 | 支持 | 普通代码文本可导出；另外对 HTML Widget / artifact 也做了专项适配。 |
| 图片 | 支持 | 支持普通图片、SVG、部分图片附件展示与导出；导出 HTML 中支持 `claude-image-block` / `claude-inline-svg`。 |
| 思考过程 | 未适配 | 当前没有单独的 Claude “思考过程”消息模型，也没有排除/切换思考过程的专项交互。 |

补充：

- Claude 是当前多媒体适配最复杂的平台之一。
- 除图片外，还额外支持部分 HTML Widget / 交互内容的快照化导出与预览。

### 通义千问

| 类型 | 适配情况 | 说明 |
| --- | --- | --- |
| 普通文本 | 支持 | 基于消息列表 API 提取用户消息和回复消息。 |
| 公式 | 部分支持 | 普通文本中的公式可随原文保留；当前没有单独的千问公式结构渲染专项适配。 |
| 代码块 | 部分支持 | 若代码以普通文本形式返回，通常可以保留；但没有像 ChatGPT 那样对结构化代码片段做专项转译。 |
| 图片 | 部分支持 | 当前更偏向处理助手侧图片占位与导出；用户侧 `image/url` 不会直接当成可导出图片附件。 |
| 思考过程 | 未适配 | 当前没有单独的“思考过程”消息模型。 |

补充：

- 千问消息主链路已使用网络 API，而不是只靠 DOM。
- 导出侧已对千问助手图片占位做 userscript 风格兼容。

### 豆包

| 类型 | 适配情况 | 说明 |
| --- | --- | --- |
| 普通文本 | 支持 | 可从 `single chain` 数据中提取普通文本、澄清块文本、TTS 文本等可见内容。 |
| 公式 | 部分支持 | 普通文本中的公式可原样保留；没有单独的豆包公式结构渲染专项适配。 |
| 代码块 | 部分支持 | 普通代码文本可保留；另对 artifact 文本做了抽取，但不是通用代码块模型。 |
| 图片 | 支持 | 支持图片实体 URL、图片附件、图片占位文本、导出图片归档。 |
| 思考过程 | 未适配 | 当前没有独立的“思考过程”消息层。 |

补充：

- 豆包除了普通消息外，还支持一部分 artifact 文本抽取。
- 图片能力比代码能力更完整。

### DeepSeek

| 类型 | 适配情况 | 说明 |
| --- | --- | --- |
| 普通文本 | 支持 | 基于 `history_messages` 解析 `REQUEST` / `RESPONSE` 等片段。 |
| 公式 | 部分支持 | 若公式出现在响应文本中，可原样保留；当前没有单独的 DeepSeek 公式结构渲染专项适配。 |
| 代码块 | 部分支持 | 普通 Markdown 代码块通常可显示和导出，但没有平台专属代码结构处理。 |
| 图片 | 未适配 | 当前没有明确的 DeepSeek 图片消息专项提取、预览和导出链路。 |
| 思考过程 | 支持 | 已将 `THINK` 片段单独建模为消息，支持预览、导出，并支持“排除思考过程”选择。 |

补充：

- DeepSeek 是当前“思考过程”支持最完整的平台。
- `textWithoutThought`、`hasThought`、`isThought` 相关字段与导出预览联动已经存在。

## 目前相对成熟的能力

当前扩展里，适配相对成熟的方向主要是：

1. `ChatGPT`
   - 普通文本
   - 公式
   - 代码块
   - 图片

2. `Claude`
   - 普通文本
   - 图片
   - HTML Widget / SVG / 文件附件相关导出

3. `DeepSeek`
   - 普通文本
   - 思考过程

## 目前仍建议持续补强的方向

1. 各平台统一的公式识别与渲染说明
   - 当前真正做了专项公式替换的主要是 ChatGPT
   - 其他平台更多是“原文保留”，不是结构化公式适配

2. 各平台统一的代码块结构提取
   - ChatGPT 最完整
   - 其他平台更多依赖原始文本是否本身就是 Markdown 代码块

3. 图片消息的跨平台一致性
   - ChatGPT / Claude / 豆包较完整
   - 千问、DeepSeek 仍有继续补齐空间

4. 思考过程的跨平台建模
   - 当前主要是 DeepSeek 有显式支持
   - 其他平台如后续有稳定 API 字段，可以继续扩展
